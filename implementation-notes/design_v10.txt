Movies Web UI — Design v10

1. Goal, run modes, and boundaries

Add a server-rendered English UI using Go html/template and HTMX, embedded in
the existing API binary. WEB_UI_ENABLED defaults to true: true serves the UI
and existing JSON API; false serves the API only, with no web routes, so
unknown web paths retain the existing JSON 404 behavior.

The UI is additive. Keep the existing JSON routes, statuses, response shapes,
error codes, tests, and app.NewRouter() unchanged; do not add web routes to
the legacy in-memory Lesson 7 router. Web handlers stay thin and call the
same service layer as API handlers. Do not pass GORM entities to templates.

2. Browser authentication and cookies

The browser submits credentials to POST /login. The handler calls the same
AuthService.Login used by the API, then sets the returned JWT in an
access_token cookie: HttpOnly, SameSite=Lax, Secure controlled by
COOKIE_SECURE, Path=/, and MaxAge equal to the token TTL in seconds. A
successful browser login redirects to /catalog. POST /logout clears the
cookie with the same path and security attributes, then redirects to /login.

The JSON API remains Authorization: Bearer header-only. The web layer reads
authentication only from the HttpOnly cookie; neither layer falls back to
the other credential transport. This avoids changing API clients or making
browser cookies authenticate API calls. As in Lesson 9, role claims are
embedded in the JWT: a role change does not revoke an already-issued token,
so a downgraded role may remain effective until token expiry.

3. XSS, CSRF, and state-changing requests

Storing a JWT in localStorage is risky for a server-rendered app: any
successful XSS can read and exfiltrate it, and the stolen bearer token can be
used from anywhere until it expires. JavaScript cannot read an HttpOnly
cookie. Cookies are sent automatically, however, so the UI must defend
against CSRF.

For every unsafe web request, require both a double-submit CSRF token and a
same-origin Origin check. Set a random csrf_token cookie (not HttpOnly) and
include the same value in the rendered form or HTMX X-CSRF-Token header;
compare values in constant time. Validate Origin against the request's
configured public origin and reject missing or mismatched Origin on these
requests. SameSite=Lax is an additional layer, not the CSRF defense itself.
Protect POST /login, POST /logout, and DELETE /catalog/movies/{id};
GET requests only read or render and never change state.

4. Template and output security

Use html/template only and preserve contextual autoescaping. Never use
text/template or template.HTML, template.JS, template.CSS, template.URL,
template.HTMLAttr, or similar trusted-type conversions on data. Movie title,
director, synopsis, and user name travel from service response/view-model
fields into ordinary template actions, where html/template escapes them.
Never concatenate those values into markup, script, style, or URL strings.

Render hx-confirm text and action URLs only as template values in their
escaped attribute contexts; keep route structure fixed and let form fields
carry user input. Add Content-Security-Policy: default-src 'self';
frame-ancestors 'none', X-Content-Type-Options: nosniff, and
Referrer-Policy: strict-origin-when-cross-origin.

Manual audit checklist (to tick during implementation):
[ ] grep for text/template
[ ] grep for template.HTML, template.JS, template.URL and related types
[ ] inspect for inline event handlers
[ ] inspect for inline scripts
[ ] inspect for string concatenation into HTML

5. Web route map and access matrix

Page routes redirect anonymous browser requests to /login; for HTMX requests,
unauthorized access returns 401 with HX-Redirect: /login. Authenticated users
without the required role receive 403 (a normal 403 page or an HTMX error
message). Middleware checks authentication before role authorization, so
anonymous means 401 and an authenticated but disallowed role means 403.

Route                         Anonymous   Viewer   Editor   Admin
GET  /login                   200         200*     200*     200*
POST /login                   303/401     303/401  303/401  303/401
GET  /catalog                 303         200      200      200
GET  /catalog/movies          303/401**   200      200      200
DELETE /catalog/movies/{id}   401         403      403      200
POST /logout                  401         303      303      303
GET  /assets/{path}           200         200      200      200

* An already authenticated user visiting /login is redirected to /catalog.
POST /login returns 303 on success and a generic 401 login form on failure.
** A page-style request redirects to /login; an HTMX request returns 401 and
HX-Redirect. On DELETE, anonymous requests return 401 plus HX-Redirect and
viewer/editor requests return 403. Deletion is admin-only.

6. Templates, view-models, and embedded files

Organize templates as a shared layout, reusable partials, page templates, and
an HTMX fragment set. Parse a separate template set per full page: Go template
definitions share a namespace within a set, so parsing several page files
that each define the same content block can overwrite definitions and make
the rendered page depend on parse order. The fragment set is parsed
separately and renders only the result rows/list.

Give each page its own view-model struct containing only display data and
necessary form/CSRF values. Embed templates and static assets with go:embed;
use template.ParseFS for templates and fs.Sub for the static-file subtree.
Vendor HTMX locally and serve it from the embedded assets rather than a CDN,
so the UI works offline, avoids a third-party script dependency, and fits
the same-origin content policy.

7. HTMX interactions

Interaction   Markup attributes                              Handler and failure behavior

              changed delay:300ms", hx-target="#movie-list",  return list fragment.
              hx-swap="innerHTML"
Genre filter  hx-get="/catalog/movies", name="genre",         Reuse movie listing service;
              hx-trigger="change", hx-target="#movie-list",   return filtered fragment.
              hx-swap="innerHTML"
Delete        hx-delete="/catalog/movies/{id}",               Admin-only; on success return
              hx-target="closest tr", hx-swap="outerHTML",    empty 200 response to remove
              hx-confirm="..."                                the row; 401/403/404 leave it.

HTMX does not swap 4xx/5xx responses by default. A small same-origin app.js
listens for htmx:responseError, displays a safe generic message using
textContent, and leaves the page data/markup unswapped. It must not echo
untrusted response content as HTML.

8. Single-binary verification plan

Build with CGO_ENABLED=0 go build -o /tmp/movies-api ./cmd/api. Create an
empty temporary directory, copy only that binary into it, configure the
required environment variables (including WEB_UI_ENABLED=true and a valid
JWT secret), run it, then curl /catalog and an embedded static asset. Also
repeat with WEB_UI_ENABLED=false and confirm /catalog has the API's JSON 404.
This verifies that templates and static files are embedded and do not need
the source tree at runtime. It does not embed PostgreSQL: a reachable external
PostgreSQL instance and migrated schema remain required.

9. Open decisions and chosen positions

- Anonymous HTMX DELETE: return 401 with HX-Redirect to /login; an
  authenticated viewer/editor gets 403. This follows authentication-before-
  authorization and gives the browser a clear login transition.
- Delete permission: admin-only; do not grant delete to editors.
- Movie status display: show a release-status badge derived from release
  information, not an availability field or new persisted business rule.

Three decisions to be ready to justify:
1. HttpOnly cookies protect the JWT from direct JavaScript reads while keeping
   the JSON API's existing explicit Bearer-header contract.
2. Double-submit CSRF validation plus Origin checking addresses ambient
   cookie authentication; SameSite=Lax is defense in depth.
3. Separate page template sets prevent shared define-name collisions, while
   embedded same-origin assets make deployment a single-binary UI.
