Security design — Movies API

1. Roles and least privilege

- viewer: may read movies and their own profile. This is the default for every
  API registration; users cannot select their own role.
- editor: has viewer access and may create or replace movies. Editors cannot
  delete movies or manage users.
- admin: may do everything, including deleting movies and managing user roles.
  Role management is restricted to admins to prevent privilege escalation.
- The first admin is created only by a seed command, never through public
  registration. The seed command must be run as a trusted operator.

2. Access control matrix

Statuses below are the successful response for an allowed request, 401 for an
anonymous request that needs authentication, and 403 for an authenticated user
without the required role. Resource validation/not-found errors can still apply.

| Endpoint | Anonymous | Viewer | Editor | Admin |
|---|---:|---:|---:|---:|
| POST /api/v1/auth/register | 201 | 201 | 201 | 201 |
| POST /api/v1/auth/login | 200 | 200 | 200 | 200 |
| GET /api/v1/movies | 200 | 200 | 200 | 200 |
| GET /api/v1/movies/:id | 200 | 200 | 200 | 200 |
| GET /health | 200 | 200 | 200 | 200 |
| GET /swagger/*any | 200 | 200 | 200 | 200 |
| GET /api/v1/me | 401 | 200 | 200 | 200 |
| POST /api/v1/movies | 401 | 403 | 201 | 201 |
| PUT /api/v1/movies/:id | 401 | 403 | 200 | 200 |
| DELETE /api/v1/movies/:id | 401 | 403 | 403 | 204 |
| GET /api/v1/users | 401 | 403 | 403 | 200 |
| PUT /api/v1/users/:id/role | 401 | 403 | 403 | 200 |

3. DTOs and mass-assignment protection

- RegisterRequest accepts only {email, password, name}; LoginRequest accepts
  only {email, password}; UpdateRoleRequest accepts only {role}.
- UserResponse exposes {id, email, name, role, created_at}, never credentials.
- The server assigns user ID and registration role. Clients cannot submit
  role during registration, user ID, or password_hash; bind only the dedicated
  request DTO fields rather than decoding requests into persistence models.
- The internal User.PasswordHash field has the json:"-" tag so it cannot be
  serialized accidentally. Password hashes are never returned by handlers.

4. Passwords and email identity

- Hash passwords with bcrypt.DefaultCost. Require at least 8 bytes and at most
  72 bytes; bcrypt ignores bytes after 72, so longer input must be rejected.
- Trim and lowercase email before storage and lookup. Enforce uniqueness
  case-insensitively in the database as well as at registration.
- Compare hashes with bcrypt's constant-time comparison. For an unknown email,
  compare against a precomputed dummy bcrypt hash before returning the same
  generic authentication error, reducing account-enumeration timing signals.

5. JWT access tokens

- Sign JWTs with HS256. Claims are user_id, role, exp (24 hours after issue),
  and iat. Require exp and accept only the HS256 signing method when parsing.
- Read the signing secret only from os.Getenv("JWT_SECRET"). On server startup,
  fail fast if it is missing or shorter than 32 bytes; never log its value.
- Clients send Authorization: Bearer <token>. A role change does not revoke
  already-issued tokens: their embedded role can remain effective until
  expiration (at most 24 hours). Immediate revocation requires a later design
  such as token versioning or a revocation store.

6. Authentication and authorization errors

- Return 401 with code "unauthorized" and message "invalid credentials" for
  both unknown email and incorrect password. Use the dummy-hash comparison
  above for the unknown-email path.
- Missing, malformed, invalid-signature, or expired bearer tokens return 401.
  Every 401 response includes WWW-Authenticate: Bearer.
- A valid authenticated identity with an insufficient role gets 403 with code
  "forbidden". Do not include token parsing, database, or credential details
  in client-facing error messages.

7. Middleware and request logging

- Register global middleware in this order: CORS, Recovery, Logging. CORS is
  outermost so recovery responses also receive CORS headers.
- On protected routes, run AuthMiddleware before RequireRole. Either middleware
  must use c.AbortWithStatusJSON on failure so no later handler runs.
- Logs may include method, path, status, and duration, but never request bodies,
  Authorization headers, passwords, password hashes, or tokens.

8. Threats (STRIDE-lite)

- Brute force / credential stuffing: bcrypt and generic login errors now;
  per-IP/account rate limits and lockout policy tracked for later.
- User enumeration: same login error and dummy-hash comparison reduce login
  enumeration; duplicate registration returns a 422 validation_error.
- Token theft/replay: short-lived signed bearer tokens now; require HTTPS in
  deployment, and consider refresh/revocation controls later.
- Stale role after downgrade: role in JWT remains effective until expiry;
  documented 24-hour maximum window, immediate revocation tracked for later.
- Mass assignment / privilege escalation: allow-listed DTOs and server-owned
  ID/registration role now; never bind requests directly to User.
- SQL injection: use GORM parameterized queries and avoid building SQL from
  user strings; review any future raw SQL.
- Oversized request bodies: enforce a small request-body limit before parsing;
  reject over-limit bodies rather than buffering them without bound. Requests
  are capped at 1 MiB with `http.MaxBytesReader`.
- Panic handling: return a generic 500 response and log no panic details.
- Weak or leaked signing secret: startup requires JWT_SECRET of at least 32
  bytes; keep it outside source control and logs, rotate through deployment.
- CORS abuse: configure an explicit trusted origin in production and do not
  enable credentialed wildcard CORS; CORS is not a substitute for auth.

Defense talking points

1. New accounts start as viewers and the first admin is provisioned out of
   band, preventing public self-promotion.
2. JWT role claims avoid a database lookup on each request, but role changes
   take effect for existing tokens only after their 24-hour expiry.
3. Unknown-user login performs a dummy bcrypt comparison and returns the same
   error as a wrong password to reduce both timing and message-based enumeration.
